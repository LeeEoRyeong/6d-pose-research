PBR은 기존 80/20 원본 목록을 그대로 참조한다. BB 개발 검증과 독립 테스트는 다르다.

## 실제 HCCEPose 요구사항

- `HccePose/bop_loader.py:train_bop_dataset_back_front.__getitem__`: RGB(BGR 정규화) 256 crop, visible mask 128, front/back 3축×8비트 HCCE 각각 24채널을 읽는다. ROI는 `bbox_visib`, 일반 pad 1.5와 augmentation; 타깃 nearest resize. 이 로더는 생성 경로에 mkdir을 시도하고 파일 누락시 XYZ를 0으로 대체하므로 원본 데이터에 그대로 연결하지 않는다.
- `HccePose/network_model.py:HccePose_BF_Net`은 EfficientNet-B4 선택 시 49채널(24+24+mask). `HccePose_Loss.forward`는 sigmoid mask L1과 예측 mask로 게이팅한 front/back code L1 및 동적 오류 history를 사용한다. `s4_p2_train_bf_pbr.py`는 front/back에 각각 3배 가중치를 적용하며 기본 `efficientnet_key=None`이므로 변경 없이 공식 B4를 파인튜닝할 수 없다. 기존 학습 스크립트는 기존 경로 쓰기를 시도한다.
- CAD+K+Pose로 투영 ROI, amodal support, CAD front/back XYZ는 만들 수 있으나, 그리퍼 등으로 가려진 픽셀의 visible mask와 올바른 실사 감독 여부는 Pose만으로 얻을 수 없다. 가림 없음이라는 이미지 단위 표시는 픽셀 단위 mask 검증이 아니다. 043/235 기존 CPU 캐시 재검사에서 gate는 모두 0이다. 기존 약한 감독 코드도 자동 가림 추정기·실제 혼합 학습 루프가 미완성이다. CAD amodal을 visible GT로 대체하거나 미확정 영역에 loss를 걸지 않는다.

## 실험 및 평가 계획

`E0.yaml`–`E3.yaml`은 실행 가능한 학습 프로그램이 아닌 차단된 설계 명세다. E0 공식 가중치 그대로, E1 BB train, E2 BB train+PBR train80, E3 PBR train80이다. 네 조건 모두 같은 고정 BB 검증 분할과 평가기를 사용한다. 실제 물리 분할, 유효 타깃 및 실행 루프가 완성되기 전 숫자·경로를 강제하지 않는다. step·optimizer·learning rate는 향후 사전 등록하고 동일 업데이트 수와 seed를 맞추며 E2 mixing ratio와 sampling도 사전 지정한다. 체크포인트 선택은 검증 명시적 symmetry ADD@0.1d 최대, 동점 시 먼저 저장한 시점; E0는 선택 없음. 검증 데이터 학습·정책 튜닝 금지.

평가 시 ADD, 최근접 ADD-S, 공식 이산 대칭 R과 t를 적용한 explicit symmetry ADD를 각각 표시한다. `itodd_symmetry_eval_20261108/symmetry.py` 검증은 동일 Pose와 `T_gt @ S`의 explicit 오차 0 PASS, 변환 순서 R'=R Rs, t'=R ts+t. PnP front-only 1.5px/150회, seed 42+frame, K와 crop 정책을 고정한다. rotation은 일반 SO(3)와 symmetry-aware를 구분, translation은 CAD units, 반환율과 명시적 대칭 성공률은 전체 평가 이미지 분모로 보고 검출 실패를 실패로 센다. Oracle ROI와 YOLO ROI 각각 보고하며 NONE/PARTIAL 별 분모도 표시한다. 확정 split이 없어 E0–E3 신규 평가와 학습 성능은 생성하지 않았다. 기존 공식 Oracle 개발27 21/27은 같은 탐색 데이터와 GT 한계가 있다. 공식 PBR 선학습과 기존 PBR20의 중복 가능성을 배제하지 못하므로 독립 테스트로 주장하지 않는다.

## CPU 검증과 구현 범위

`prepare.py`: 검수·GT·K·이미지 100건, PBR 100건의 visible mask 형식과 기존 80/20 교집합, RGB 중복, 후보 매니페스트를 검사했다. `InspectionDataset`은 실제 이미지·K·R,t만 읽는 **검사용 로더**이며 `training_sample`은 의도적으로 예외를 낸다. 실제 학습 로더와 optimizer/trainer는 아직 구현되지 않았다. `checks.py`: 공식 체크포인트 1,488개 tensor 엄격 로드 CPU PASS; 기존 043/235 CAD 캐시의 K·크기·crop·HCCE (128×128×24)와 gate=0 확인. `target_previews/`는 CAD amodal과 front/back의 진단 시각화이며 visible GT가 아니다. 기존 smoke의 학습 loss 비교/CPU forward는 과거 결과로만 참고하며 이번에는 재실행하지 않았다.

## Phase 15 차단 해소 순서

1. 촬영 기록·그룹 검수를 통해 물리적 배치 경계 확정, 필요하면 독립 세션 추가 촬영 후 split freeze 및 중복 검사.
2. 실사 visible mask를 검수해 확보하거나, 가림 의심 픽셀을 제외하는 신뢰 가능한 약한 감독 gate를 독립적으로 검증한다. 어느 쪽도 현 자료만으로 자동 충족하지 않는다.
3. 공식 대칭 기반 XYZ/HCCE 대표 좌표 규약을 실사/PBR 양쪽에 구현하고 공통 round-trip·투영·기존 라벨 차이를 검증한다. 기존 PBR 라벨을 바로 사용하지 않는다.
4. 원본과 분리된 학습 loader/trainer, 그룹 제한 sampler, E0–E3 평가/checkpoint 선택, 빈 gate와 누출 방지 테스트를 구현한다. 사전 등록된 실험 설정과 CPU smoke test를 완성한다.
5. 실사 GT의 정밀도와 실제 척도는 별도 측정으로 확인한다. 그 전 평가 수치는 검수된 개발 조건의 제한적 결과다. 위 조건 충족 및 사용자 승인 후에만 GPU 파인튜닝.
