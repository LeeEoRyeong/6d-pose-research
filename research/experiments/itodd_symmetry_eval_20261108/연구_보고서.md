# ITODD obj04 공식 가중치: 대칭 검증 및 실사·PBR 추론 비교

작성일: 2026-11-08 (KST). 공식 EfficientNet-B4와 기존 ResNet34 checkpoint를 **학습 없이** 같은 평가기로 평가했다. 대칭 계산 검증을 통과한 뒤 공식 모델의 실사 개발 5장을 먼저 추론했고, 그다음 두 모델 각각 실사 개발 27장과 PBR Val20을 평가했다. BB 실사 100장은 처리하지 않았다.

## 결과와 해석

임계값은 공식 obj04 diameter 139.379의 10%인 **13.9379 CAD 단위**다. BOP CAD는 mm 단위이며 실사 pose의 물리 단위는 CAD와 같다고 가정한 개발 평가다. 모든 pose 판정은 GT oracle ROI 조건이다.

| 모델 / 평가 데이터 | PnP 유효 | 일반 ADD < 0.1d | ADD-S < 0.1d | 명시적 대칭 ADD < 0.1d |
|---|---:|---:|---:|---:|
| 공식 EfficientNet-B4 / 실사 개발27 | 27/27 | 0/27 | 26/27 | 21/27 |
| 기존 ResNet34 / 실사 개발27 | 27/27 | 0/27 | 0/27 | 0/27 |
| 공식 EfficientNet-B4 / PBR Val20 | 20/20 | 4/20 | 10/20 | 9/20 |
| 기존 ResNet34 / PBR Val20 | 20/20 | 1/20 | 3/20 | 1/20 |

**실사 개발 27장에서는 공식 모델이 명시적 대칭 오차 기준 21/27, ADD-S 기준 26/27로 기존 baseline보다 높았다.** 다만 원본 GT는 거친 시각 정합 기준이고 066/068/070/072/073은 기존에 판단 불가로 표시됐으며, 평가 ROI는 GT CAD를 투영한 oracle이다. 독립 최종 테스트·detector 포함 end-to-end 성능이나 정밀 계측 정확도로 해석하지 않는다. 동일 모델의 일반 ADD 0/27과 대칭 고려 결과가 크게 다른 것은 세 지표의 의미가 다르기 때문이다. 공식 모델 실사 27개는 모두 명시적 대칭 지표의 최소 오차가 비항등 대칭에서 선택됐다.

기존 ResNet34의 이번 실사 ADD 평균은 129.04549로 이전 개발 평가의 129.0455와 일치하고, PBR 일반 ADD pass 역시 기존 1/20이 재현됐다. PnP 유효는 단지 solver가 유한한 정면 pose를 반환했음을 의미하며 정확한 pose라는 뜻은 아니다. 공식 BOP AR과 이 자체 ADD/ADD-S 수치는 서로 비교하지 않는다.

## 대칭 변환과 지표 검증

공식 [models_info.json](/RESEARCH_DATA/HCCEPose_experiments/itodd_official_audit_20261108/official_models_info.json)의 obj04 이산 대칭 `S`는 회전과 모델 좌표 translation을 모두 포함한다. BOP model-to-camera pose `T=[R,t]`에서 동등 후보는 **`T′=T S`**, 즉 `R′=R R_s`, `t′=R t_s+t`다. 공식 `t_s`의 z 성분은 -0.144095다. 사용자의 기존 GT나 라벨은 수정하지 않고 평가 시 후보 좌표만 계산했다.

- 동일 예측/GT에서 일반 ADD, ADD-S, 명시적 대칭 ADD 모두 0.
- 비항등 대칭을 적용한 예측은 일반 ADD 74.21439, 최근접점 ADD-S 0.70409, 명시적 대칭 ADD 0.0. 대칭 고려 지표는 0.1d 안이다.
- 행렬 합성과 점별 두 단계 변환의 최대 차이는 약 1.14e-13이다. 회전만 적용하고 이동을 누락하면 카메라 translation에 약 0.144095 CAD 단위 차이가 생긴다.
- ADD-S의 Numpy 전체 최근접점 계산을 별도의 OpenCV BFMatcher 완전탐색과 대조한 차이는 약 2.91e-6이다. [대칭 검증 수치](symmetry_validation.json), [독립 ADD-S 교차검증](independent_adds_validation.json), [구현](symmetry.py).

일반 ADD는 같은 vertex index 간 거리의 평균이다. ADD-S는 각 예측 vertex에서 가장 가까운 GT vertex까지 거리의 평균이다. 명시적 대칭 ADD는 항등과 공식 이산 대칭을 **GT pose 오른쪽에 합성한 각 경우의 대응 vertex 평균 거리 중 최소값**이다. 이는 본 실험에서 정의한 명시적 대칭 지표이며 BOP의 AR, MSSD 또는 MSPD 점수라고 부르지 않는다. 공식 대칭은 mesh의 점 샘플에 완벽히 일치하는 변환은 아니므로 대칭 pose의 ADD-S는 0이 아닌 약 0.704다. 반면 명시적 지표는 그 변환을 동등하다고 정의하므로 0이다. ADD-S는 최근접점을 독립적으로 고르기 때문에 명시적 대칭 ADD보다 관대한 결과가 나올 수 있다.

## 입력·추론 조건

- 공식 모델: [공식 가중치](/RESEARCH_DATA/HCCEPose_experiments/itodd_official_audit_20261108/itodd_obj04_1_0000step50000.pt), EfficientNet-B4; 기존 baseline: [best_val_loss.pt](/RESEARCH_DATA/HCCEPose_experiments/obj04_seminar_v1/runs/baseline_seed42_20261103_214353/trained_only/checkpoints/best_val_loss.pt), epoch155 ResNet34. 둘 다 `strict=True`로 로드했다. 공식 checkpoint는 NumPy 스칼라 타입만 지정해 `weights_only=True`로 읽었다.
- 두 모델에 같은 BGR ImageNet 정규화, 객체 bounds, HCCE decode, 예측 mask > 0.5, Front 좌표 기반 원본 `solve_PnP`, RANSAC EPNP `pnp_op=2`, 1.5 px, 150회와 `42+frame` seed를 적용했다. 예측 Back XYZ도 저장했으나 PnP 입력은 기존 baseline과 동일하게 Front만 사용했다.
- PBR은 기존 split의 20장, 해당 프레임 K와 **GT visible bbox pad1.5**를 사용했다. 실사 개발은 RAW를 K,D로 remap하고 output K=원 K, **GT CAD 투영 bbox pad1.5**를 사용했다. 두 데이터셋 간 ROI 정의는 다르지만 각 데이터셋 내 두 모델의 ROI는 같다. 실사 보정 RGB 27장은 이전 통제 PNG와 배열이 모두 동일했다.
- 모델 구조와 학습 이력이 다르므로 이 결과는 공식 checkpoint와 baseline의 실용적 비교다. backbone 또는 데이터만의 인과 효과로 분리하지 않는다. 공식 가중치는 BOP PBR을 사용했으므로 PBR Val20을 독립 검증으로 주장하지 않는다. 기존 [sampling_and_provenance.json](/RESEARCH_DATA/HCCEPose_experiments/realistic_final100/sampling_and_provenance.json)은 Val이 포함된 `realistic_100` 생성 경로와 자체 camera sampling을 기록하지만, 공식 BOP PBR 전체와의 원본 이미지 해시 대조·학습 manifest는 없어 중복 여부는 미확정이다.

## Fine-tuning 판단과 보존

공식 모델은 이 oracle ROI 실사 개발셋에서 강한 출발점이므로 **fine-tuning 설계와 독립 검증을 이어갈 가치가 있다**. 다만 현재 높은 개발셋 결과만으로 fine-tuning이 필요하거나 개선된다고 단정하지 않는다. 우선 독립 촬영·검증된 GT와 실제 detector ROI에서 공식 모델을 평가하고, 이전 weak-supervision 코드의 real gate는 신뢰 가능한 자동 가림 추정기 검증 전까지 0으로 유지한다. PBR val의 공식 학습 중복 여부와 실사 train/test 촬영 구간 누출도 확인해야 한다. 기존 실사27 반복 사용은 개발셋 과적합 위험이 있다.

이번 실행에서 GPU 학습·fine-tuning은 없었다. 두 모델의 PyTorch peak allocated는 공식 약 395.7 MiB, baseline 약 373.3 MiB였으며 다른 GPU 시스템 메모리는 포함하지 않는다. 읽어들인 입력·checkpoint 등 85개 파일의 SHA-256은 평가 전후 동일했다. 기존 코드·모델·GT와 이전 결과를 덮어쓰지 않았다. 전체 실행 코드는 [evaluate.py](evaluate.py)이며 재실행 시 새 run 디렉터리를 만든다.
