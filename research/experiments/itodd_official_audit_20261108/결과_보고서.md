# 공식 ITODD obj04 체크포인트·CAD 호환성 검토

작성 2026-11-08 KST. **strict 로드 PASS, pose 정확도 평가 보류.** 공식 ITODD obj04와 현재 BB/PBR의 CAD 파일은 완전히 같지만, 공식 대칭 정의가 현재 PBR 라벨에 반영되지 않았고 BB 보정 영상의 출력 K 이력이 확정되지 않아 요청된 전체 좌표계·평가 호환성을 아직 확정할 수 없다. 평가 조건을 임의로 바꾸거나 이 차이를 무시하지 않았다. PBR Val20과 실사 개발27 모두 공식 모델 및 기존 baseline의 이번 재평가를 실행하지 않았고, 예측 mask/XYZ/pose overlay나 새로운 ADD(-S)를 생성하지 않았다.

공식 [논문](https://arxiv.org/html/2510.10177)의 BOP 실험 설명은 7개 core 데이터셋에 BOP 제공 PBR을 사용했고, real training은 YCB-V/T-LESS/TUD-L에 추가했다고 한다. 따라서 ITODD 학습의 일반적 설명은 PBR이다. 다만 obj04 파일 자체에는 전체 데이터 manifest·정확한 학습 scene 목록이 없어, 이 체크포인트의 각 단계와 샘플을 개별 확인한 것은 아니다. [공식 저장소](https://github.com/WangYuLin-SEU/HCCEPose)는 BF 가중치가 front-only 모델로부터 fine-tuning된다고 설명한다. 체크포인트의 `best_score=1.0`, `iteration_step=50000`은 저장된 메타데이터이며 점수의 계산 조건은 독립 확인되지 않았다. BOP 공식 AR이나 현재 실사 정확도로 해석하지 않는다.

## 모델 및 strict 로드

- 현재 [BOP 시험 스크립트](/RESEARCH_DATA/HCCEPose/s4_p2_test_bf_pbr_bop_challenge.py:73)는 `efficientnet_key=1`, 3채널 입력을 사용한다. `network_model.py` 실제 구현에서는 이 값이 **EfficientNet-B4** 분기를 고른다. 기존 연구 baseline의 `efficientnet_key=None`은 ResNet34 분기이므로 두 체크포인트는 서로 같은 backbone이 아니다.
- 공식 체크포인트의 입력 stem은 `[48,3,3,3]`, 최종 head는 `[49,280,1,1]`이다. 현재 코드의 출력은 mask 1채널과 HCCE front 24채널 / back 24채널이다. 추론은 HCCE decode를 0–255에서 정규화한 뒤 mesh의 `min_xyz` 및 `size_xyz`로 객체 XYZ를 복원한다. 이 3채널 구조는 RGB 입력이 가능하다는 뜻이며, ITODD 촬영의 광학 도메인과 현재 RGB 촬영이 동일하다는 뜻은 아니다. ITODD는 회색조 카메라를 사용한다. [MVTec 원본 데이터셋 설명](https://www.mvtec.com/research-teaching/datasets/mvtec-itodd)
- CPU에서 PyTorch `weights_only=True`와 필요한 NumPy scalar/dtype만 allowlist하여 체크포인트를 읽었다. 모델 1,488개 키와 체크포인트 1,488개 키, 전체 tensor shape가 일치했다. 누락 0·추가 0·shape 불일치 0이며 **`load_state_dict(..., strict=True)` PASS**다. 임의 변환이나 `strict=False`를 사용하지 않았다. 기록: [checkpoint_audit.json](checkpoint_audit.json), [검사 코드](audit_load.py).
- 기존 baseline 체크포인트는 그대로 보존했다. 학습 데이터와 checkpoint를 수정하거나 optimizer 학습을 실행하지 않았다.

## CAD·좌표계

[BOP 공식 ITODD 모델](https://huggingface.co/datasets/bop-benchmark/itodd/tree/main)의 `itodd_models.zip`은 5,504,325 bytes이고 공식 LFS SHA-256 `07d04c647a615e9965eed20442198ccff121d5ff1f8864352f47c5aaf0f6a651`과 일치한다. 여기서 추출한 `models/obj_000004.ply`, 현재 BB 개발 CAD 및 실험 PBR CAD는 SHA-256 **`0933ba753a7aa8d673df6fa180e35807869903661b1bc8d1419ebb0ac890424f`로 완전 일치**한다. 파일 내용상 ASCII PLY, 정점 1,439개, 삼각형 2,970개도 동일하다. 단일 파일 hash 일치는 CAD 좌표계와 mesh 데이터가 동일하다는 강한 근거이지, BB 영상 속 물리 물체가 이 CAD와 완벽히 동일하다는 독립 검증은 아니다.

정점 bounding box는 x/y `[-45.25,45.25]`, z 약 `[-32.65764,32.65764]`이고 bbox 중심은 (0,0,0)이다. BOP 데이터는 모델 좌표를 mm 단위로 표기한다. BB 개발 GT translation의 물리 단위와 실제 물체 치수는 기존 검사상 CAD와 **동일 수치 단위라고 가정**할 수 있으나 독립 실측은 없다. 동일 mesh hash 때문에 임의의 축 회전·scale·origin 변환을 적용할 근거는 없다.

공식 `models_info.json`의 obj04에는 이산 대칭 1개가 지정되어 있다. 회전은 대략 `[[0,-1,0],[-1,0,0],[0,0,-1]]`, 대칭의 모델 좌표 translation은 z `-0.144095`다. [공식 모델 정보](official_models_info.json). 반면 기존 실험의 [models_info.json](/RESEARCH_DATA/HCCEPose_experiments/obj04_seminar_v1/data/models/models_info.json)은 대칭 항목이 없다. 공식 min/size의 소수점 반올림 외에 mesh는 동일하지만 대칭은 의미 있는 규약 차이다. 현재 [renderer label 생성 코드](/RESEARCH_DATA/HCCEPose/HccePose/bop_loader.py:609)는 대칭 정보가 있으면 `pnp_solve_re_4p` 및 `modified_sym_Rt`로 대표 pose를 바꾼다. 기존 PBR의 CPU 생성 라벨은 대칭 항목 없는 정보로 만들었다. 공식 체크포인트의 실제 라벨 생성 시 설정과 현재 라벨의 canonicalization이 일치한다고 확인할 수 없다.

참고로 공식 대칭 변환을 모든 공식 정점에 적용한 뒤 원래 mesh의 가장 가까운 정점까지 거리의 평균은 0.704, 중앙값 0.264, p95 3.743, 최대 6.036 CAD 단위였다. 이는 정점 샘플링을 포함하는 근사 진단이며 공식 대칭 정의의 정확도나 물리적 측정 오차 자체를 증명하지 않는다. 기존 baseline 보고서의 ADD와 대칭을 고려한 ADD-S를 동등하게 취급할 수 없다. 향후 두 모델 모두에 동일한 사전 고정 대칭 처리와 ADD/ADD-S 규칙을 적용하고 baseline을 다시 평가해야 한다.

## 카메라·undistortion

BOP 공식 ITODD 기본 camera.json은 1280×960, fx 2992.14, fy 3003.49, cx 633.412, cy 489.882다. 현재 BB JSON 100장의 K는 모두 기존 실사 calibration K와 수치적으로 같으며, 1280×720, fx 984.70009004, fy 983.75715611, cx 635.41416344, cy 362.61850196이다. 서로 다른 카메라 K인 것 자체는 이상이 아니다. 해당 영상의 정확한 K를 투영 및 PnP에 사용해야 한다.

기존 실사 개발 27장에는 RAW에서 distortion D를 사용하고 output K를 원 K로 지정해 보정한 27장과 관련 선행검사가 있다. 그러나 BB 100장의 기존 `rgb_undistorted`가 정확히 어떤 newK·crop·resize로 생성됐는지는 확정되지 않았다. 두 영상 유형의 서로 다른 전처리를 섞어 같은 K라고 가정해서는 안 된다. 개발27 GT는 이전 시각 검토에서 일부 프레임의 정밀도 판단이 불가했으며 독립 최종 테스트가 아니다.

## 판단 및 남은 작업

**평가 보류:** 대칭 canonicalization 불일치가 공식 checkpoint와 기존 PBR Front/Back 코드의 비교·PnP·대칭 점수에 미치는 영향, BB 보정 영상의 newK, 실사 물체·GT의 독립적인 대응이 아직 검증되지 않았다. 따라서 사용자 조건에 따라 Val20/실사27 pose 정확도 및 baseline의 동일 평가기 재평가를 시작하지 않았다. 구조적 strict 로드 PASS만으로 이 조건이 충족됐다고 간주하지 않는다.

**Fine-tuning 검토 가치:** 같은 CAD와 완전한 strict 로드를 확인했으므로 공식 EfficientNet-B4 가중치를 초기값으로 검토할 가치는 높다. 다만 지금은 fine-tuning도 성능 개선도 입증되지 않았다. 공식 ITODD 연구용 자산에 적용되는 이용 조건을 확인해야 한다. MVTec ITODD 데이터셋은 [CC BY-NC-SA 4.0](https://www.mvtec.com/research-teaching/datasets/mvtec-itodd)로 표기된다. 가중치 자체의 별도 라이선스와 의존 데이터의 조건은 사용 목적에 맞춰 확인한다.

다음 단계는 (1) 공식 대칭을 PBR과 실사 pose에서 어떻게 처리할지, GT label과 symmetry-aware ADD-S/ADD를 같은 평가기로 검증하고, (2) 기존 개발27의 명시적 RAW→K,D→newK=K 전처리와 RGB oracle ROI를 그대로 재사용하며 BB100 K 이력을 별도로 확인하고, (3) 사전 조건이 성립할 때에만 동일 evaluator·mesh·시드·ROI·K·PnP로 기존 A와 공식 가중치를 재평가하는 것이다. 공식 checkpoint는 BOP PBR 데이터를 이미 학습했으므로 기존 20장의 합성 출처와 학습 overlap 가능성도 확인한다. 평가 결과는 자체 ADD(-S)로만 보고하며 공식 BOP AR과 직접 비교하지 않는다.
