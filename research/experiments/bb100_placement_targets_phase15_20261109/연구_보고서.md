# Phase 15 — BB100 배치 구간과 실사 감독 타깃

작성 2026-11-10 KST. 사용자 확인에 따르면 물체 정지 시 그리퍼 등 주변만 움직이고 물체를 재배치하면 Vision6D Pose를 다시 맞췄으며, 촬영 순서가 유지됐다. 동일 Pose 재사용은 정상 라벨링 방식이다. 이 진술은 개별 경계나 정밀 GT를 자동으로 인증하지 않는다.

## 단계별 판정

| 항목 | 판정 | 이유와 해결 |
|---|---|---|
| Placement Split | **REVIEW_REQUIRED** | 39개 연속 Pose 구간은 자동 후보, 경계 99개는 미검수다. 검수 CSV로 실제 재배치와 비재배치를 확인하고, 멀리 떨어진 구간의 동일 배치 가능성을 함께 묶어 split을 확정해야 한다. |
| Visible Mask | **BLOCKED** | BB 픽셀 단위 검수 완료 visible mask를 찾지 못했다. SAM 4장과 CAD 교집합은 미검수 후보다. 개별 가림 영역·구멍 검수 또는 독립적으로 검증된 가림 추정이 필요하다. |
| HCCE Targets | **BLOCKED** | CAD 기준 amodal 및 비대칭 정규화 전 front/back 진단 맵과 실행 시 24채널 HCCE를 만들 수 있다. 공식의 대칭 대표 Pose 선택과 VisPy rasterization 일치, 실제 visible gate는 미검증이다. |
| Fine-tuning Pipeline | **BLOCKED** | 확정 분할·감독 타깃 및 실제 학습 로더/루프가 없다. Phase 14 E0–E3 YAML은 설계 명세이며 실행 가능한 학습 설정이 아니다. |

학습이나 GPU 추론은 수행하지 않았다. 기존 307개 소스 파일의 Phase 12 기록 SHA-256과 현재 해시는 일치하며, 검수 CSV의 SHA-256도 유지됐다. 해시 검사는 해당 307개와 CSV 범위다.

## 입력·카메라·Pose 재검증

Phase 14의 읽기 전용 검사를 재사용하고 검수 100건(ACCEPT 100, NONE 39, PARTIAL 61), 고유 수치 Pose 36개 및 기존 PBR train80/val20을 재대조했다. 100장 영상 크기 1280×720, 원본 K 및 Pose와 BOP JSON 매칭 검사, SO(3) 행렬 및 유한 병진 검사는 Phase 14 PASS다. 동일 Tapo와 전처리는 사용자 확인 및 기존 수치 재현에 근거하며 정밀 물리 인증은 아니다. 카메라 출력 K=입력 K, 왜곡 보정은 기존 결과를 재사용한다. PBR 100장 중 80/20은 기존 split을 보존한다. 공식 B4 checkpoint는 Phase 14 CPU `strict=True` PASS 결과를 재사용했다.

## 촬영 순서와 구간

프레임 ID 오름차순과 `frame_mono` 촬영순이 100장 전부 일치한다. 프레임 번호는 불연속이며 번호 차이를 시간 차로 해석하지 않고 실제 timestamp를 쓴다. 수치상 Pose가 인접 프레임에서 바뀔 때 새 `placement_###`를 시작하면 **39개 후보 구간과 Pose 변경 38개 경계**가 나온다. 같은 Pose에서도 물체가 움직였을 가능성을 검토하도록 동일 Pose 간 61개 경계까지 포함해 전체 99개 경계를 제공한다. 이 값은 실제 배치 수나 확정된 경계가 아니다.

연속하지 않은 구간에서 동일 Pose 그룹 31, 43, 44가 재등장한다. 동일 수치 Pose·정확히 같은 RGB 또는 동일 배치 의심은 다른 split으로 보내지 않아야 하지만, 동일 Pose 반복만으로 오류나 배치 동일성을 확정하지 않는다. 경계뿐 아니라 비인접 구간들의 같은 실제 배치 여부도 추가로 확인해야 한다.

CSV의 회전은 일반 SO(3) 상대각, 병진은 CAD 좌표 단위 거리다. 실제 BB 척도의 독립 계측이 없으므로 mm 실측으로 부르지 않는다. 투영 위치 변화는 GT 원점의 계산 결과이고, 객체 ROI 회색 차이·KLT·edge 변화는 이전 CAD amodal 영역에서 계산했다. 주변 그리퍼·반사·가림에 반응하므로 물체 이동 추정치일 뿐 움직임의 인증이나 픽셀 GT가 아니다. 포인트가 부족하면 수치를 비워둔다.

우선 볼 경계 예시는 109→221(11.283초, 187.41 CAD 단위, GT 원점/ROI 큰 변화), 90→93(0.275초, 22.21 단위, ROI 회색 MAE 68.68), 235→237(동일 Pose, ROI MAE 23.81, KLT 82점)이다. 마지막 사례에서 KLT는 그리퍼를 추적할 수 있으므로 객체 움직임으로 단정할 수 없다. 검수 HTML의 Phase 12 RGB·CAD 비교에서 외곽과 구멍의 고정 위치를 살펴보고 가림 때문에 판단할 수 없는 경계는 UNCERTAIN으로 둔다.

## 경계 검수 및 분할

Windows에서는 `BB100_placement_review_windows.zip` 전체를 복사·해제한 뒤 `index.html`을 Chrome에서 오프라인으로 연다. 각 카드에서 **ACCEPT = 두 프레임 사이 실제 재배치 경계**, **REJECT = 경계가 아님**, **UNCERTAIN = 판단 불가**다. 상태·메모는 localStorage와 CSV로 기록하며 CSV 내보내기·가져오기를 지원한다. localStorage는 소실될 수 있으므로 CSV를 내보내 별도 보관한다. 기존 100장 ACCEPT는 투영 시각 검수이지 경계 ACCEPT가 아니다. 내보낸 CSV를 서버로 옮긴 다음에도 비인접 동일 배치 검토와 분할 검사가 필요하다.

기존 보수 연결군 221/31을 쓰면 학습 64장(NONE 24/PARTIAL 40, Pose 19)과 검증 36장(NONE 15/PARTIAL 21, Pose 17)의 초안이다. 이 초안은 동일 수치 Pose·자동 placement·연결군·완전 동일 RGB 해시의 교집합이 0이지만, 촬영이 같은 세션이고 실제 물리적 독립성이 확정된 것은 아니다. 따라서 `approved_split`은 전부 UNASSIGNED다. 현재 두 연결군을 보존하면 70:30, 80:20에 더 가깝게 맞출 수 없고 무작위 seed가 적용되지 않았다. 새로운 물리 배치 그룹이 확인되면 미리 seed를 정한 group split과 가림 분포를 재검사한다. 두 그룹만 있으면 Group K-Fold도 2-fold에 불과하며 독립 세션 검증을 대체하지 않는다. 별도 독립 테스트는 없다.

## 원본 학습 규약과 생성 타깃

- `HccePose/bop_loader.py:train_bop_dataset_back_front.__getitem__`은 visible mask, bbox_visib, front/back 좌표 PNG를 직접 읽고 256 RGB crop, 128 mask 및 24+24채널 HCCE를 만든다. Full mask는 데이터 경로 구성 등에 이용되나 이 loss의 직접 타깃은 visible mask다. 학습 로더는 미리 생성한 XYZ를 읽으므로 각 샘플의 pose/K를 loss에 직접 전달하지 않지만, 이 맵을 렌더링하려면 CAD, GT Pose, K가 필요하다.
- `rendering_bop_dataset_back_front.__getitem__`은 near/far depth로 XYZ를 만들며 `pnp_solve_re_4p`와 `modified_sym_Rt`로 이산 대칭 대표 Pose를 선택한다. 대칭 변환에는 R뿐 아니라 t도 포함된다. 렌더러의 표면 정의·좌표 변환·대칭 처리는 별도 확인이 필요하다.
- `network_model.py:HccePose_BF_Net`은 B4에서 mask 1, front/back 각각 24채널을 내고, `HccePose_Loss.forward`는 mask 손실과 예측 mask로 gate한 코드 손실 및 동적 history를 계산한다. 빈 gate를 안전하게 제외하는 약한 감독 방식은 원본 loss와 별도 구현·검증해야 한다.

`amodal_masks/pose_*.png`와 `xyz_raw_front/`, `xyz_raw_back/`는 36개 수치 Pose별 CPU 렌더를 저장하고 `target_quality.csv`에서 각 100개 프레임이 이를 참조한다. 기존 CPU 렌더러의 최소/최대 깊이, 공식 모델 AABB 정규화와 uint8 quantization, 원본 crop/HCCE 함수를 재사용했다. **이 XYZ는 공식 대칭 대표 Pose 보정 전 진단용이며 학습 정답이 아니다.** 36개 렌더를 100개 프레임으로 재사용한 것은 수치 Pose와 K가 일치하기 때문이다. 네 개 SAM 후보와 CAD 교집합은 `visible_candidates/`에 저장했으며 미검수·비GT다. 나머지 96장의 visible mask를 생성하거나 가림 신뢰도를 임의로 부여하지 않았다.

비교: 기존 10장 라벨링 도구의 초기 mask는 CAD amodal이며 검수 완료 visible GT가 아니다. 기존 SAM은 4장 실험에서 구멍 누락과 일부 후보의 그리퍼 포함이 관찰됐다. 소량 수동 마스크는 시간은 들지만 검증 참조를 제공한다. CAD∩SAM은 CAD 밖 잘못된 영역을 줄일 수 있지만 SAM의 그리퍼 오검출, 투영 오차, CAD 경계 오차를 보장하지 않는다. `NONE`이라는 프레임 단위 표식도 픽셀별 가시성을 보증하지 않는다. PARTIAL에서는 가림 의심과 미확정 픽셀을 mask/XYZ loss 및 동적 history에서 제외해야 하며, 현재 안전한 gate를 입증하지 못해 모두 0으로 둔다.

## 품질 검사와 한계

100장에 대해 mask/XYZ 경로와 해상도, 0/255 CAD mask, uint8 XYZ 범위, 배경 0을 검사했다. 36번의 CPU 렌더에서 support 내부 depth 유한 및 front≤back, 진단 HCCE crop 24×128×128, gate=0을 확인했다. 양자화 XYZ를 같은 입력 Pose·K로 재투영한 p99 최대는 0.486px 미만이다. 이는 자기 일관성 검사이며 **실제 RGB 또는 공식 VisPy와의 독립적인 정합도/정밀 Pose 정확도 지표가 아니다**. 실제 RGB와의 정렬은 사용자 CAD 투영 시각 ACCEPT를 이용하며 별도 픽셀 오차 검증은 없다.

BB 043/235에 대한 CPU 진단 로더, 256 crop 및 front/back HCCE, 빈 gate 학습 차단 PASS. PBR 0/10의 기존 비대칭 보정 전 front/back PNG는 동일 CPU 렌더 경로와 픽셀 단위 일치했다. PBR 라벨과 공식 대칭 타깃이 일치한다는 의미는 아니다. NONE 39장의 CAD support 평균 17,151px, PARTIAL 61장 18,242px이며 각각 유효 실사 감독 픽셀 0이다. 면적은 가림 정답률이나 실제 mask 품질 지표가 아니다.

ZIP의 이미지 100개와 99개 경계의 상대 참조 및 압축 무결성 PASS. Linux headless Firefox에서 99개 카드, 이미지, 판정 변경·복원, 필터와 인용 CSV 파싱 PASS. 실제 Windows Chrome과 내보낸 파일의 전체 왕복 조작은 이 서버에서 검증하지 않았다.

## 다음 단계

1. 99개 인접 경계를 검수하고, 비인접 구간에 재등장하는 동일 Pose와 동일 물리 배치를 묶어 보수 split을 확정한다. 모호한 경계가 남으면 분할을 확정하지 않는다.
2. 대표 NONE/PARTIAL에서 픽셀 참조를 마련해 visible mask 또는 선택적 신뢰 gate의 오검출을 평가한다. 확인된 픽셀만 loss와 동적 history에 사용한다.
3. 공식 대칭 선택 및 동일 RGB/pose/K에 대한 독립 VisPy 타깃 비교를 구현하고, front/back·HCCE 역변환·가림 gate를 검증한다. 이 검증을 통과할 때까지 현 진단 XYZ를 학습에 쓰지 않는다.
4. 분리된 실제 학습 loader/trainer, 확정 split 적용, 누출 테스트, 빈 gate 처리 및 CPU smoke를 구현한 뒤에만 사용자 승인 하에 학습한다.
